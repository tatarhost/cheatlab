# CheatLab Mail — архитектура и требования для запуска

Статус: интеграция отправки/получения через Resend реализована в ветке функции. Она не работает, пока не настроены секреты Worker, вебхук, миграция D1 и развёртывание.

## Продуктовый контракт

- Почтовые адреса используют домен `@cheatlab.fun`.
- Каждый существующий аккаунт CheatLab может владеть не более чем пятью почтовыми ящиками.
- Идентичность почтового ящика отделена от идентичности входа в CheatLab. Существующие сессии по нику/паролю остаются полномочием аккаунта; создание почтового ящика требует аутентифицированной сессии.
- Сообщения, вложения и настройки почтового ящика приватны для владеющего аккаунта. Публичные ресурсы Cloudinary никогда не должны использоваться для приватной почты.
- Не показывайте почтовый ящик как активный, пока провайдер не подтвердит, что адрес/домен подготовлен.
- Никогда не заявляйте, что сообщение доставлено, пока почтовый провайдер не вернёт успешный результат отправки.

## Существующее приложение

Репозиторий уже представляет собой статический фронтенд на GitHub Pages плюс API Cloudflare Worker, Cloudflare D1, KV и Cloudinary для публичных медиа. Существующая система аккаунтов — это собственная схема с ником/паролем в `worker/src/accounts.js` и `worker/src/index.js`; это не Firebase Authentication. Не заменяйте её на Firebase без плана миграции. Браузерный apiKey Firebase — не учётные данные почтового сервера, а Cloudinary — это CDN для медиа, а не хостинг почтовых ящиков.

## Предлагаемая архитектура

1. **Фронтенд:** добавьте раздел Mail в существующую оболочку приложения; сохраните текущий чёрно-белый дизайн и используйте сдержанные полупрозрачные стеклянные поверхности для почтового рабочего пространства.
2. **Идентичность:** переиспользуйте существующую сессию CheatLab. Ограничение в пять почтовых ящиков должно соблюдаться в Worker и в ограничении/транзакции базы данных; никогда не доверяйте клиентскому счётчику.
3. **API почты:** аутентифицированные маршруты Worker для списка/создания/переименования/удаления почтовых ящиков, просмотра входящих/отправленных, состояния прочтения, составления, отправки и скачивания вложений. Применяйте лимиты частоты на аккаунт и на почтовый ящик, строгую проверку получателя, проверки CSRF/origin и меры против злоупотреблений.
4. **Входящие:** направляйте почту домена в специальный обработчик email Worker. Разбирайте MIME поддерживаемым MIME-парсером, проверяйте получателя конверта на соответствие активному почтовому ящику и сохраняйте сообщение до подтверждения получения.
5. **Исходящие:** используйте проверенного провайдера отправки с SPF, DKIM и DMARC. Ставьте отправки в очередь, записывайте ID сообщений провайдера и отказы, применяйте лимиты отправки на аккаунт и мониторинг злоупотреблений.
6. **Хранилище:** D1 хранит метаданные почтовых ящиков/сообщений; приватное объектное хранилище (предпочтительно Cloudflare R2) хранит сырой MIME и вложения. Держите приватные объекты электронной почты отдельно от публичных медиа Cloudinary. Соблюдайте квоты и ограничения размера вложений.
7. **Безопасность:** TLS при передаче, приватный доступ к объектам через аутентифицированные эндпоинты Worker, санитизация HTML при отображении, определение типа содержимого вложений, сканирование на вредоносное ПО где доступно, защита паролей/сессий, события аудита, удаление/экспорт аккаунта и контроль хранения.

## Модель данных почтового ящика (планируемая)

- `mailboxes`: id, owner_user_id, local_part, address, status, created_at, updated_at. Уникальный address и уникальный (owner_user_id, local_part).
- `mail_messages`: id, mailbox_id, owner_user_id, direction, envelope_from, from_header, to_header, cc_header, subject, text_body, sanitized_html_key, raw_object_key, provider_message_id, in_reply_to, is_read, received_at, sent_at, deleted_at.
- `mail_attachments`: id, message_id, object_key, filename, mime_type, size_bytes, content_id.
- `mail_outbox`: id, owner_user_id, mailbox_id, recipient, payload_object_key, status, attempts, provider_message_id, last_error, created_at, sent_at.

Worker должен обеспечивать ограничение в пять почтовых ящиков атомарно (например, транзакцией/условной вставкой), а не через отдельную гонку «сначала подсчёт, потом вставка».

## Реальность бесплатного тарифа и блокер развёртывания

Cloudflare Email Routing может принимать почту и направлять её в Worker на бесплатном плане, но сам по себе не является размещённым IMAP-ящиком. Текущая документация Cloudflare Email Sending говорит, что исходящая отправка произвольным получателям доступна на Workers Paid; бесплатный план ограничен проверенными адресами назначения. Cloudflare Email Service также требует, чтобы домен использовал Cloudflare DNS и был подключён в панели Cloudflare.

Следовательно, действительно работоспособный публичный почтовый сервис (приём и отправка на произвольные внешние адреса) не может быть активирован только коммитом кода в GitHub. Для этого требуется:
- контроль над DNS-зоной `cheatlab.fun` и изменение/добавление записей MX, SPF, DKIM и DMARC;
- почтовый провайдер/аккаунт или собственный почтовый сервер с публичным IP, обратным DNS, TLS, средствами против злоупотреблений и постоянным хранилищем;
- приватные учётные данные/конфигурация провайдера и развёртывание Worker плюс привязки базы данных/объектного хранилища.

GitHub Pages — это статический хостинг, он не может запускать демоны SMTP/IMAP. Один лишь бесплатный сервис пересылки входящих не является полноценным почтовым ящиком. Не развёртывайте фальшивый входящий ящик и не принимайте почту, которую нельзя надёжно сохранить.

## Предварительные условия развёртывания

Рабочий процесс развёртывания сайта публикует только `public/` в GitHub Pages. Worker и схема D1 развёртываются отдельно. После слияния и проверки этой ветки примените миграцию командой `cd worker && npx wrangler d1 migrations apply cheatlab --remote --config wrangler.toml`, затем разверните командой `npx wrangler deploy --config wrangler.toml`. Эти команды требуют аутентифицированного аккаунта Cloudflare с доступом к существующей базе данных D1. Это не активирует внешнюю доставку почты; подключение провайдера и проверка DNS остаются отдельными требованиями.

- Этап 0: проверьте владение DNS домена, текущий аккаунт/зону Cloudflare, доступный план Worker и привязки приватного хранилища.

- Этап 2: обработка входящих MIME и приватное объектное хранилище; интеграционные тесты.
- Этап 3: интеграция провайдера исходящей почты, обработка отказов, лимиты частоты и сквозные тесты с внешними почтовыми ящиками.
- Этап 4: интерфейс веб-почты, поиск, папки/метки, черновики, вложения, адаптивный стеклянный дизайн, доступность и проверка безопасности.

## Учётные данные

Никогда не коммитьте API-токены, SMTP-пароли, приватные ключи, API-секреты Cloudinary или учётные данные сервисного аккаунта Firebase. Помещайте учётные данные провайдера в секреты Cloudflare Worker. Веб-конфигурация Firebase публична по своей природе, но всё равно требует строгих правил безопасности Firestore/Storage, если Firebase используется для каких-либо отдельных целей. Одного API-ключа Cloudinary недостаточно для подписи приватных загрузок; API-секрет должен оставаться на сервере.
